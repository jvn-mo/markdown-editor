## Electron

### [2026-07-13] Electron IPC 通信与 dialog API

#### 一、是什么（What）
Electron 的 IPC（Inter-Process Communication）是主进程（Node.js）和渲染进程（Chromium）之间的通信桥梁。

类比：主进程像餐厅后厨（负责文件、窗口、系统API），渲染进程像前台服务员（负责界面交互），IPC 像传菜口，双方通过它安全地传递数据和指令。

#### 二、为什么用它（Why）
在这个项目中，渲染进程需要：
- 保存文件到磁盘（主进程才有 Node.js 的 fs 权限）
- 弹出系统保存对话框（dialog API 只在主进程可用）
- 导出 PDF（需要创建隐藏窗口调用 printToPDF）

如果不用 IPC，渲染进程直接调用 Node.js API 会引入安全风险（XSS 攻击可直接读写文件）。

#### 三、怎么用（How）
**基础用法**：
```javascript
// preload.js（桥梁）
const { contextBridge, ipcRenderer } = require('electron');
contextBridge.exposeInMainWorld('electronAPI', {
  saveFile: (content, filePath) => ipcRenderer.invoke('save-file', content, filePath)
});

// main.js（主进程处理）
ipcMain.handle('save-file', async (event, content, filePath) => {
  // ... 调用 dialog.showSaveDialog 和 fs.writeFileSync
});

// renderer.js（渲染进程调用）
const result = await window.electronAPI.saveFile(content, path);
```

**在本项目中的实际应用**：
```javascript
// 导出 PDF 时传递默认文件名
ipcMain.handle('export-pdf', async (event, htmlContent, theme, defaultFileName) => {
  const result = await dialog.showSaveDialog(mainWindow, {
    defaultPath: defaultFileName || 'export.pdf',
    filters: [{ name: 'PDF', extensions: ['pdf'] }]
  });
  // ...
});
```

#### 四、底层原理（深入理解）
Electron 基于 Chromium 的多进程架构。每个窗口是一个独立的渲染进程，主进程负责协调。

- `ipcRenderer.invoke` 发送一个可等待的异步请求
- 主进程的 `ipcMain.handle` 注册处理器，返回 Promise 结果
- `contextBridge.exposeInMainWorld` 是安全的关键：它只暴露白名单 API，阻止渲染进程直接访问 `require('fs')`

#### 五、常见坑与解决方案
| 坑 | 现象 | 原因 | 解决 |
|----|------|------|------|
| 直接在 renderer 使用 require | 报错 `require is not defined` | contextIsolation 开启后渲染进程无 Node 环境 | 通过 preload.js 暴露 API |
| dialog 在 renderer 调用无响应 | 对话框不弹出 | dialog 模块只能在主进程使用 | 通过 IPC 让主进程代调用 |
| 传递函数或 DOM 元素 | 报错或数据丢失 | IPC 通过 Structured Clone 序列化，不支持函数/DOM | 只传递可序列化的纯数据 |

#### 六、面试关联
**面试官可能会问**：
> Q1：为什么 Electron 要分主进程和渲染进程？
> A1：Chromium 本身就是多进程架构，每个标签页是独立进程，避免一个页面崩溃影响整个浏览器。Electron 继承了这一点，主进程负责应用生命周期和系统API，渲染进程负责UI，通过 IPC 通信保证安全和稳定。
>
> Q2：contextIsolation 是什么？为什么重要？
> A2：contextIsolation 把 preload 脚本和渲染进程的 JavaScript 上下文隔离。开启后，即使网页被 XSS 攻击，恶意代码也无法直接访问 Node.js API。配合 contextBridge 只暴露必要的安全 API，是 Electron 安全最佳实践。

**项目经历话术**：
> "在这个 Markdown 编辑器项目中，我需要让前端界面调用系统文件对话框和导出 PDF。由于安全限制，渲染进程不能直接访问 Node.js 的 fs 和 dialog 模块。我通过 preload.js 作为安全桥梁，用 contextBridge 暴露必要的 IPC API，主进程通过 ipcMain.handle 处理实际的文件操作。这样既实现了功能，又保证了安全性。"

- 前置知识：Node.js 事件循环、Promise/async-await
- 后续扩展：Electron 安全最佳实践（CSP、上下文隔离、禁用 remote 模块）

## 前端状态管理

### [2026-07-13] Vanilla JS 多标签页状态管理

#### 一、是什么（What）
在没有 React/Vue 等框架的情况下，用原生 JavaScript 维护多个打开文件的状态（内容、路径、历史记录、是否修改）。

类比：就像一张办公桌上有多个文件夹（tabs），每个文件夹里有独立的手稿（content）和修改标记（isDirty），你同一时间只能看一个文件夹，但可以在它们之间切换。

#### 二、为什么用它（Why）
这个项目使用 Vanilla JS + Electron，没有引入前端框架。当需要支持"同时打开多个 Markdown 文件并切换"时，需要自己实现状态管理。

核心优势：轻量，无需引入 Vuex/Redux 等库，代码量少，可控性强。

#### 三、怎么用（How）
**基础设计**：
```javascript
let tabs = [];
let activeTabId = null;

function createTab(filePath, content) {
  return {
    id: nextTabId++,
    filePath,
    fileName: getFileName(filePath),
    content,
    isDirty: false,
    history: [content],
    historyIndex: 0
  };
}

function switchTab(tabId) {
  // 保存当前内容到旧标签
  const oldTab = getActiveTab();
  if (oldTab) oldTab.content = editor.value;
  
  // 加载新标签内容
  const newTab = tabs.find(t => t.id === tabId);
  editor.value = newTab.content;
  activeTabId = tabId;
}
```

#### 四、底层原理
本质上是"单一数据源 + 手动同步 DOM"。
- `tabs[]` 是唯一数据源
- 编辑器输入时更新 `tab.content`
- 切换标签时，手动将 `tab.content` 写回 textarea
- 每个标签独立维护 `history[]` 数组实现撤销/重做

#### 五、常见坑与解决方案
| 坑 | 现象 | 原因 | 解决 |
|----|------|------|------|
| 切换标签丢失未保存内容 | 回到标签 A 发现内容是标签 B 的 | 切换时没把 textarea 内容保存回旧 tab | switchTab 时先 `oldTab.content = editor.value` |
| 撤销栈混乱 | 在标签 A 撤销，影响了标签 B | 全局只有一个 history 数组 | 每个 tab 独立维护自己的 history |
| 重复打开同一文件 | 打开 `a.md` 两次，有两个标签 | 没有去重逻辑 | openFile 时先 `findTabByPath(filePath)` |

#### 六、面试关联
> Q1：不用框架怎么管理复杂状态？
> A1：我会根据功能设计一个中心化的状态对象（如 tabs 数组），所有修改都通过这个对象进行，DOM 更新是状态的反映。对于更复杂的场景，可以自己实现简单的发布-订阅模式。
>
> Q2：和 Vue/React 的状态管理相比，原生方案的优劣？
> A2：原生方案轻量、无依赖、学习成本低，但缺乏响应式自动更新，需要手动同步 DOM。对于这个项目，状态不复杂，原生方案足够。如果状态更复杂或需要组件间大量通信，引入框架会更高效。

## CSS 主题系统

### [2026-07-13] CSS data-attribute 主题隔离

#### 一、是什么（What）
使用 HTML 元素的 `data-*` 属性作为 CSS 选择器条件，实现同一页面不同区域的独立主题切换。

类比：就像一间房子有两盏灯，一盏暖光一盏冷光，你可以分别控制它们的开关，而不是只能统一开暖光或统一开冷光。

#### 二、为什么用它（Why）
用户希望编辑区用暗色主题（保护眼睛），但预览区用亮色主题（更接近最终输出效果）。传统的全局 class 切换无法做到区域隔离。

#### 三、怎么用（How）
```css
/* 编辑器亮色主题 */
body[data-editor-theme="light"] #editor {
  background: #ffffff;
  color: #333333;
}

/* 预览暗色主题 */
body[data-preview-theme="dark"] .preview-pane {
  background: #1e1e1e;
}
body[data-preview-theme="dark"] .preview-content {
  color: #d4d4d4;
}
```

```javascript
function setEditorTheme(theme) {
  document.body.setAttribute('data-editor-theme', theme);
}
function setPreviewTheme(theme) {
  document.body.setAttribute('data-preview-theme', theme);
}
```

#### 四、底层原理
CSS 属性选择器 `[attr="value"]` 的优先级与 class 相同。通过在 body 上设置两个独立的 data 属性，可以用纯 CSS 控制不同子树的样式，无需 JavaScript 逐个修改元素样式。

#### 五、面试关联
> Q1：除了 class 切换，还有什么方式实现主题切换？
> A1：可以使用 CSS 变量（custom properties）或 data-attribute 选择器。CSS 变量适合同一套颜色值的全局替换，data-attribute 适合需要完全独立的样式规则。这个项目两者结合：data-attribute 控制整体主题，CSS 变量可以进一步细化颜色值。

## pandoc 与文档转换

### [2026-07-14] pandoc Markdown 扩展与 DOCX 导出

#### 一、是什么（What）
pandoc 是一个通用的文档转换工具，支持通过扩展（extensions）控制 Markdown 的解析行为，如 `pipe_tables`（管道表格）、`hard_line_breaks`（硬换行）、`tex_math_single_backslash`（LaTeX 公式）。

类比：pandoc 像一台多功能打印机，扩展就像不同的打印模式——照片模式、文档模式、海报模式，同一台机器可以按需求调整输出效果。

#### 二、为什么用它（Why）
项目需要将 Markdown 内容导出为 DOCX 格式供用户编辑。marked.js（预览渲染）和 pandoc（DOCX 导出）对 Markdown 的解析存在差异：
- marked.js 默认把单换行当硬换行（`<br>`）
- pandoc 遵循标准 Markdown，单换行合并为同一段落
- marked.js 对表格格式较宽松（前可无空行、分隔符可有空格）
- pandoc 要求表格前有空行，分隔符不能有空格

#### 三、怎么用（How）
**基础用法**：
```bash
# 标准转换（表格、换行按标准 Markdown 处理）
pandoc input.md -o output.docx --from markdown --to docx

# 启用管道表格和硬换行
pandoc input.md -o output.docx --from markdown+pipe_tables+hard_line_breaks --to docx
```

**在本项目中的实际应用**：
```javascript
// 导出前预处理：规范化换行、表格前补空行、清理分隔符空格
markdownContent = markdownContent.replace(/\r\n/g, '\n').replace(/\r/g, '\n');

// 表格前自动插入空行
const lines = markdownContent.split('\n');
const resultLines = [];
for (let i = 0; i < lines.length; i++) {
  const line = lines[i];
  const isTableLine = /^\s*\|/.test(line);
  const prevLine = resultLines.length > 0 ? resultLines[resultLines.length - 1] : null;
  const prevIsTable = prevLine !== null && /^\s*\|/.test(prevLine);
  const prevIsEmpty = prevLine === null || prevLine.trim() === '';
  if (isTableLine && !prevIsTable && !prevIsEmpty) {
    resultLines.push('');
  }
  resultLines.push(line);
}
markdownContent = resultLines.join('\n');

// 清理分隔符行空格
markdownContent = markdownContent.replace(/^\s*\|(?:\s*-+\s*\|)+\s*$/gm, (line) => {
  return line.replace(/[^|\-]/g, '');
});

// pandoc 命令
const pandocCmd = `pandoc "${tempMd}" -o "${result.filePath}" --from markdown+tex_math_single_backslash+pipe_tables+hard_line_breaks --to docx`;
```

#### 四、底层原理
Markdown 标准规定：段落内的单换行等价于空格，只有空行才分隔段落。这是为了兼容纯文本的可读性（一行不要太长）。但不同渲染器对此的处理不同：
- GitHub Flavored Markdown（GFM）默认也遵循此规则
- marked.js 如果开启 `breaks: true`，则单换行当 `<br>`
- pandoc 的 `hard_line_breaks` 扩展强制把单换行当硬换行

#### 五、常见坑与解决方案
| 坑 | 现象 | 原因 | 解决 |
|----|------|------|------|
| 表格在 DOCX 中不被识别 | 表格内容和文字混在一起 | 表格前无空行，或分隔符含空格 | 预处理时补空行并清理分隔符 |
| 单换行在 DOCX 中丢失 | 多行文字合并为一段 | pandoc 按标准 Markdown 处理 | 添加 `+hard_line_breaks` 扩展 |
| 字体不是宋体 | DOCX 中文字显示为其他字体 | pandoc 默认使用 Calibri | 用 adm-zip 修改 word/styles.xml 中的 `w:eastAsia` |

#### 六、面试关联
> Q1：pandoc 是什么？和直接写 Word 有什么区别？
> A1：pandoc 是一个通用文档转换器，支持 Markdown、DOCX、PDF、LaTeX 等几十种格式互转。它的优势是自动化——写一次 Markdown，可以批量导出为多种格式，适合技术文档和论文写作。缺点是它对 Markdown 的解析比浏览器渲染器更严格，需要了解扩展配置。
>
> Q2：如果预览和导出效果不一致，你会怎么排查？
> A2：首先确认两个渲染器的解析差异。比如本项目预览用 marked.js，导出用 pandoc。我会用最小复现案例分别测试两者，找到差异点后，在导出前做预处理（如补空行、清理格式），或调整 pandoc 扩展参数，使两者行为对齐。

**项目经历话术**：
> "在这个 Markdown 编辑器项目中，我发现预览能正常显示的表格和换行，导出 DOCX 后却失效了。原因是 marked.js 和 pandoc 对 Markdown 的解析标准不同。我通过 pandoc 扩展（`+pipe_tables+hard_line_breaks`）和导出前预处理（自动补空行、清理分隔符空格），最终让 DOCX 导出效果和预览完全一致。"

## Electron 打包与部署

### [2026-07-14] Electron asar 打包后资源路径问题

#### 一、是什么（What）
Electron 打包应用时，源代码会被打包为 app.asar 归档文件。asar 是一种只读归档格式，文件系统操作（如 `require('./package.json')`）在 asar 中的行为可能与开发环境不同。

类比：开发环境像直接在书架找书（文件系统），打包后像把书装进密封箱（asar），虽然还能打开箱子取书，但路径解析方式变了。

#### 二、为什么用它（Why）
Electron 应用需要打包分发。asar 打包可以：
- 减少文件数量，提升启动速度
- 保护源代码（只读，不易直接篡改）
- 减小安装包体积

但副作用是：相对路径 require、fs.readFile 等操作可能失效或行为异常。

#### 三、怎么用（How）
**基础用法**：
```javascript
// ❌ 开发正常，打包后可能失效
const packageJson = require('./package.json');

// ✅ 使用 Electron 内置 API 或 IPC
// 主进程中
const { app } = require('electron');
const version = app.getVersion(); // 自动读取 package.json 的 version

// preload 中通过 IPC 获取
const version = ipcRenderer.sendSync('get-app-version');
```

**在本项目中的实际应用**：
```javascript
// main.js
ipcMain.on('get-app-version', (event) => {
  event.returnValue = app.getVersion();
});

// preload.js
let appVersion = '1.0.2';
try {
  appVersion = ipcRenderer.sendSync('get-app-version');
} catch (e) {
  console.error('Get version error:', e);
}

contextBridge.exposeInMainWorld('electronAPI', {
  // ...
  appVersion: appVersion
});
```

#### 四、底层原理
asar 是 Electron 基于 tar 格式设计的只读归档，通过 Node.js 的 `fs` 模块劫持实现透明访问。但 `require` 的模块解析算法在某些情况下无法正确处理 asar 内的相对路径（尤其是动态 require 或非标准入口文件）。

最佳实践：
- 主进程中用 `app.getVersion()`/`app.getPath()` 替代直接读取文件
- 渲染进程中通过 IPC 让主进程代劳文件操作
- preload 中避免动态 require，尽量使用 `contextBridge` 暴露的确定性 API

#### 五、常见坑与解决方案
| 坑 | 现象 | 原因 | 解决 |
|----|------|------|------|
| require 相对路径失效 | 打包后报错 `Cannot find module` | asar 中路径解析与文件系统不同 | 用 IPC 或 Electron 内置 API 替代 |
| __dirname 指向异常 | 路径指向 asar 内部而非预期位置 | asar 虚拟化了文件系统 | 使用 `app.getAppPath()` 或 `process.resourcesPath` |
| 静态资源加载失败 | 图片/CSS 不显示 | asar 只读，某些加载方式不支持 | 将资源放到 `extraFiles` 或 `files` 配置中 |

#### 六、面试关联
> Q1：Electron 打包后有哪些常见问题？
> A1：最常见的是路径问题。开发时直接用 `require('./config.json')` 或 `fs.readFile` 能工作，但打包成 asar 后路径解析会变化。我的做法是：主进程用 `app.getVersion()` 等内置 API，渲染进程通过 IPC 通信获取数据，避免在 preload 中做动态文件读取。
>
> Q2：asar 是什么？为什么 Electron 要用它？
> A2：asar 是 Electron 设计的只读归档格式，类似 tar。打包后整个应用的源代码变成一个文件，减少文件句柄开销、提升启动速度，还能一定程度上保护代码。代价是某些文件系统操作需要调整。

**项目经历话术**：
> "在打包 Electron 应用时，我发现 preload.js 中 `require('./package.json')` 开发正常，但安装包运行后版本号获取失败。排查后发现 asar 打包改变了相对路径的解析行为。我改为在主进程中用 `app.getVersion()` 获取版本号，通过 IPC 同步传递给 preload，这样既解决了路径问题，也符合 Electron 安全最佳实践。"

## 项目经历话术库
1. "在这个 Markdown 编辑器项目中，我使用 Electron IPC 实现了渲染进程与主进程的安全通信，通过 preload.js 的 contextBridge 暴露必要 API，主进程负责实际的文件读写和 PDF 导出。"
2. "项目中我使用 Vanilla JS 实现了一个轻量的多标签页状态管理系统，每个标签独立维护内容、文件路径和撤销历史，通过中心化状态对象和手动 DOM 同步实现了流畅的切换体验。"
3. "为了满足用户对编辑区和预览区不同主题的需求，我使用 CSS data-attribute 选择器实现了区域级主题隔离，编辑区暗色、预览区亮色可以独立配置。"
4. "在 DOCX 导出功能中，我发现预览和 pandoc 导出效果不一致。通过 pandoc 扩展（`+pipe_tables+hard_line_breaks`）和导出前预处理（自动补空行、清理分隔符空格），最终让导出效果和预览完全一致。"
5. "打包 Electron 应用时，我遇到 asar 打包后 preload 中相对路径 require 失效的问题。最终通过主进程的 `app.getVersion()` 配合 IPC 同步通信获取版本号，既解决了路径问题，也遵循了安全最佳实践。"
